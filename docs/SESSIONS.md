# Sessions, LAN and optional Steam

Both graphical clients start at a main menu. Choose **Single player**, choose a doctrine, then **Start match**. Return to the main menu from preparation, combat or drafting to dispose that authority; the next game gets a fresh match identity. Music and local preferences belong to the application and survive session replacement.

Godot uses a session Node with ENet and Godot reliable RPCs. MonoGame uses an ordinary disposable C# session with LiteNetLib 2.1.4. They have independent protocols and do not connect to each other. Game.Core is unchanged and owns admission, ownership, sequencing, costs, readiness, combat and rewards. A guest has no simulation authority. Solo commands reach the same Core validation directly without a socket.

## Hosting and joining LAN games

Run `mise run play-godot` or `mise run play-monogame`. Choose **Host LAN** in one instance. Guests enter `host:port` and choose **Join / reconnect LAN**. Defaults are UDP **27025** for Godot and **27026** for MonoGame. Allow that UDP port through your own firewall when playing across machines. Hosting can start with one through four total players.

The lobby shows admitted cities, host, local player, connected status, doctrines and remaining city slots. Choose your own doctrine and let the host start. Lobby membership has no second readiness toggle. Preparation uses Core's existing all-player readiness. Every participant builds, recruits and drafts their own rewards. The shared combat arena includes all players.

The unchanged Core retains an admitted city when its player leaves, including in a lobby. A slot count therefore describes unallocated cities, not free network connections. Reconnect to reclaim that city. Start another hosted session for a completely fresh roster. New cities cannot join a match after it starts.

Development launches use your normal display and audio:

```sh
mise run dev-godot-multiplayer                  # host + one guest
mise run dev-monogame-multiplayer -- --players 4
mise run dev-godot-multiplayer -- --players 1  # host only
```

These launches own temporary, isolated settings/resume directories, removed when their supervisor ends. Use ordinary play launches for persistent reconnect credentials. Close any supervised client or press Ctrl-C to close the group.

Raw client options are also accepted:

```sh
mise run play-godot -- --host 27025
mise run play-godot -- --join 192.168.1.20:27025
mise run play-monogame -- --host 27026
mise run play-monogame -- --join 192.168.1.20:27026
```

`--port` changes the menu's hosting port. `--data-path /private/directory` overrides credential storage. Rendering stays local: `play-*-assets` works with the same network sessions and missing sprites fall back to shapes. No artwork is required.

## Reconnection and failure

Choose **Reconnect** after a lost connection, or return to the menu and join the same endpoint. Restarting a guest process can reclaim its existing city. The original running authority continues combat while guests are absent. Host exit ends the session; there is no host migration, authority save or recovery after a host crash.

Private resume files bind endpoint, implementation, transport, match and next command sequence. Steam additionally binds AppID and original host, and Core checks the transport-authenticated remote identity. LAN tokens are generated by Core using cryptographic randomness. Credential files are written atomically with mode 0600 at creation on Unix. They contain the last exact command for safe retry as well as the reserved next sequence. They never enter snapshots, screenshots, lobby metadata or public diagnostics.

Godot defaults to its `user://sessions` directory; MonoGame defaults to the platform application-data directory under `common-watch-v2/monogame`. Only one client process should use a particular data directory at a time. Automated workers always isolate these directories. **Join LAN as new player (forget resume)** explicitly discards the previous LAN credential; use this when connecting to a replacement match at the same address.

Every replacement session owns fresh callbacks and pending requests. Disposed sessions ignore late delivery. Handshake attempt IDs and match guards reject old welcomes; snapshot revisions cannot move backward. Commands reserve a sequence on disk before delivery, wait for an authoritative acknowledgment and retry the same serialized request. Retrying an accepted command uses Core's existing ledger rather than spending or recruiting again.

Full snapshots use the original bounded Brotli codec and compatibility validation, with a 16 MiB decompression ceiling. MonoGame messages have a 512 KiB encoded ceiling and reliable fragmentation is bounded. Snapshot delivery permits one outstanding snapshot per admitted guest, acknowledged separately from gameplay commands; an unresponsive receiver is disconnected after ten seconds. This bounds reliable backlog. Core's ordered retained event history travels with every snapshot. If history has expired, playback explicitly switches to the current authoritative baseline and reports recovery. No delta codec or individual scene-node replication is used.

## Optional Steam

Set **`COMMON_WATCH_STEAM_APP_ID`** to your own authorized Steam AppID. No test or production AppID is assumed. Ordinary offline/LAN startup makes no Steam SDK initialization request. Steam buttons can initialize on demand; `play-*-steam` additionally enables invitation handling at startup. A missing SDK/login/configuration leaves offline and LAN play available. `COMMON_WATCH_STEAM_DISABLED=1` prevents initialization during offline verification.

```sh
COMMON_WATCH_STEAM_APP_ID=YOUR_AUTHORIZED_ID mise run play-godot-steam
COMMON_WATCH_STEAM_APP_ID=YOUR_AUTHORIZED_ID mise run play-monogame-steam
```

Choose **Host private Steam lobby**. **Invite Steam friends** opens Steam's native friend invitation overlay. Launch the application through Steam when the overlay requires Steam launch/injection. An accepted warm invitation uses a confirmation before leaving a current game; cold `+connect_lobby LOBBY_ID` arguments are supported. For exported Godot applications launched by Steam, use launch options `-- --steam` so engine and game arguments stay separate; MonoGame uses `--steam`. Godot also reads the SDK launch command line for cold invitations. A lobby ID can also be entered directly. The host checks native lobby membership as well as the authenticated socket identity. Lobby membership only permits a transport attempt: Core admission and a valid compatible initial snapshot are still required.

Each engine advertises a different V2 identity, transport version 1, Core protocol 16, AppID, original host, GUID match and lobby/in-progress state. Credentials and private city data are absent. An ownership change in Steam ends a guest session rather than transferring authority. Reconnection uses the original authenticated Steam host.

Godot pins GodotSteam **4.22.1 GDExtension / SDK 1.65**, including Linux/Windows x64 binaries and original license/manifest. Runtime loading and C# peer conversion were checked with pinned Godot **4.7.2 .NET**. `tools/prepare-godot.sh` registers that extension for runtime launches without invoking the editor or initializing the SDK. MonoGame pins official Facepunch **2.5.2** release binaries for .NET 6+ and Linux/Windows x64; .NET 10 compiles against these. NuGet's public Facepunch 2.3.3 package contains an older Windows-only assembly, so the official release's separate POSIX/Win64 assemblies and matching native libraries are vendored with SHA-256 manifests. No alternate Steam wrapper was introduced. MonoGame uses Steam Networking Sockets `CreateRelaySocket`/`ConnectRelay`, reliable sends and SDK-authenticated connection identities; callbacks and task results are consumed on the application thread.

## Agent verification commands

All commands run at the repository root. `mise run test` includes Core/shared, offline Steam logic and the real graphical/process integration suites.

| Concern | Commands, using `CLIENT` = `godot` or `monogame` |
| --- | --- |
| Build and upstream regressions | `mise run build`, `test-core`, `test-shared`, `test` |
| Menu/solo/native controls | `mise run test-CLIENT-session` |
| Actual two-, three-, four-player LAN gameplay | `mise run test-CLIENT-multiplayer` |
| Lobby integration and actual frames | `mise run test-CLIENT-lobby`, `capture-CLIENT-lobby` |
| Resume and failure/admission checks | `mise run test-CLIENT-reconnect`, `test-CLIENT-network-faults` |
| Offline Steam state/metadata/authentication logic | `mise run test-CLIENT-steam` |
| Optional interactive Steam | `mise run play-CLIENT-steam` |
| Explicit live Steam workers | `mise run test-CLIENT-steam-native -- host FRIEND_STEAM_ID` or `-- guest LOBBY_ID` |

Lobby commands reuse the complete actual multiplayer exercise, including paid construction, readiness, combat, independent drafting and identical wave-two snapshots. Reconnection commands include protocol rejection, ownership attacks, duplicate delivery, process restart, preparation/combat/draft reconnect, exact accepted-command retry, invalid/expired credentials, roster lock, capacity, lobby departure and host shutdown. All process supervisors have bounded timeouts, isolated UDP ports and user data, terminate their process groups and own an Xvfb display on Linux. Python 3 and the existing graphical prerequisites are required; no system packages are installed by tasks. Interactive dev tasks keep normal audio; only automated checks use silent drivers.

Actual lobby frames are written to `artifacts/captures/CLIENT/lobby-{2,3,4}p.png`. Process logs are under `artifacts/test-logs`. Development control/report switches are opt-in verification instrumentation; they only submit commands or observe detached snapshots.

## Native Steam verification gate

Native Steam SDK/account tests have **not been executed** here. Mock tests, native library loading, ABI conversion and LAN tests do not prove Steam connectivity, invitations, relay routing or authenticated reconnection.

Use two eligible accounts with access to the configured AppID, normally on separate machines. Explicitly authorize each worker:

```sh
export COMMON_WATCH_STEAM_APP_ID=YOUR_AUTHORIZED_ID
export COMMON_WATCH_STEAM_NATIVE_AUTHORIZED=1
mise run test-godot-steam-native -- host FRIEND_STEAM_ID
# On the second account/machine, use the printed lobby ID:
mise run test-godot-steam-native -- guest LOBBY_ID
```

Use `test-monogame-steam-native` for a separate MonoGame pair. The host explicitly submits one invitation to the supplied existing Steam friend; it does not enumerate or choose recipients automatically. Workers require real SDK initialization and Steam transport, drive the legal two-player opening through combat/drafting, and have the guest reconnect to its retained city. Reports go to `artifacts/native-steam/CLIENT/{host,guest}.json`; a guest report must have `steam: true` and `reconnected: true`. Automated workers own an Xvfb display, silent test audio and temporary private settings/credential directories. The host remains alive for the guest's reconnect; Ctrl-C closes it, with an overall ten-minute bound. Verify friend invitation/acceptance using the native UI separately, inspect SDK connection/relay evidence, and confirm both applications shut down cleanly. A report alone does not certify overlay delivery or that a particular connection actually selected a relay route.

Live verification remains an explicit prerequisite to calling Steam end-to-end functionality qualified. Windows binaries can be published, but actual Windows runtime/network qualification is also unexecuted.
